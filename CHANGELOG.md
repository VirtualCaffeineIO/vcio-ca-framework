## 2026.9.1 — 2026-09-11

Closes the findings from the third external review pass. **Fresh deployment only** until the F2 upgrade test is recorded in [Docs/upgrade.md](Docs/upgrade.md).

Finding numbers below are the section IDs of the 2026.9.1 work order (revision 3, from the ruled adjudication of 2026-09-11), which is the authoritative list this release was built against.

**Not lab-validated.** 2026.7.1 shipped after a full import into a live tenant. This release has not had one: F1 (device matrix), F2 (upgrade) and F3 (CA601 targeting and enforcement) all need a lab tenant, and F2 additionally needs Windows PowerShell 5.1 for IntuneManagement. Only F4 — both validators clean against the tree — has been run. Nothing here should be read as tenant-verified.

### Policy changes

* **A1 — one device filter.** `FILTER_MANAGED_OR` and `FILTER_MANAGED_AND` are gone, replaced by `FILTER_COMPLIANT` = `device.isCompliant -eq True` on CA204, CA300, CA301 and CA802. Device ownership is not a security state: a corporate-owned device that has fallen out of compliance is not a managed device, and a filter that said otherwise was excusing exactly the devices worth catching. Both old constants are deleted so nothing can reference them again. Validator rule C5 pins the remaining string.
* **A2 — CA202 and CA803 grant on compliant device OR app protection**, with no device filter at all. The old exclude-filter removed enrolled-and-compliant devices from the policy's scope, which meant an enrolled device that *fell out of* compliance was reached by neither the compliance path nor the MAM path. Now: compliant device passes on compliance, unmanaged device passes on APP, and an enrolled non-compliant device is blocked unless some other effective APP assignment reaches it — the shipped filters do not, a customer-added one might, and F1 tests for it.
* **A3 — CA001 split into CA001 (device code flow) and CA007 (authentication transfer)**, each with its own exclusion group. Teams Rooms, IoT and console devices legitimately need device code flow and go in `SG-CA-Excl-CA001`; nothing legitimate needs authentication transfer, so `SG-CA-Excl-CA007` stays empty. Sharing one group handed every device-code exception a free auth-transfer bypass. CA007 joins Ring 2, not Ring 1.
* **A4 — CA002 exempts the Directory Synchronization Accounts role** (`d29b2b05-8046-44ba-8758-1e26182fcf32`, verified against Microsoft Learn before commit, not taken from memory). `users_block()` gained `excludeRoles` to support it. The Entra Connect sync account cannot do interactive MFA, and the previous workaround — parking it in `SG-CA-ServiceAccounts` — put it behind a fence carrying the application servers' egress rather than the Connect server's. It is never a member of that group. Optional fencing for it is a dedicated `CA500-VCIO-ServiceAccounts-IPFence-DirSync` instance on `SG-CA-SA-DirSync`.
* **A5 — CA403 excludes service providers.** Blocking a GDAP partner technician from the admin portals breaks the engagement and pushes the customer toward a standing local admin account for the partner, which is worse than a governed GDAP relationship. Service providers remain governed by CA400, CA402, CA103 and their home tenant. New [Docs/partner-access.md](Docs/partner-access.md) carries the reasoning, the Ring 2 and Ring 3 tests, and the fallbacks — written down, not chosen.
* **A6 — CA700 and CA701 no longer exclude service accounts.** They are blocks, not interactive challenges: there is nothing for a non-interactive account to fail to complete, and a compromised service account is precisely what "high risk" means. The exclusion was protecting the attacker. CA702 and CA703 keep it, because they demand MFA and a password change.
* **A7 — CA601 gained an agent principal scope** (`clientApplications.includeAgentIdServicePrincipals: ["All"]`, exactly as CA600 has it). `agentIdRiskLevels` is a condition, not a scope; the policy had `includeUsers: ['None']` and no principals, which is the inert shape the validators exist to catch. Now enforced as rule C3.
* **A8 — new core group `SG-CA-Privileged`**, included on CA100, CA101 and CA102 alongside the built-in roles. Role targeting is blind to custom directory roles, AU-scoped assignments and Azure RBAC entirely — an Owner at subscription scope is control-plane privilege that the 100s never saw. Ships empty; reconciled by the new E1 tool.
* **A9 — CA801 is now the Tier 0 posture** (compliant device **AND** phishing-resistant MFA). The old Step-Up posture (compliant device *or* MFA) enforced nothing new for anyone inside CA002's MFA scope — MFA alone already satisfied it — so the slot is reused for the posture that was actually missing. Reusing it is deliberate; **retiring an old instance is a documented step, not a rename** ([Docs/upgrade.md](Docs/upgrade.md)). Redundancy of this shape is now caught by rule C4.
* **A10 — the transition set.** New core group `SG-CA-Transition-Hybrid`, plus CA204-T, CA300-T and CA301-T alongside the existing CA200-T, all targeting that group with a filter that also admits hybrid-joined devices. Standard CA200, CA204, CA300 and CA301 now exclude it, so exactly one of each pair reaches a given user. Emptying the group is the exit. The exit **date** is not in the policy JSON: Graph documents `conditionalAccessPolicy.description` as "Not used" and nothing proves a value there survives an IntuneManagement round trip, so it lives in the deployment manifest and is enforced by rule C2 plus the E2 script against an operator deadline. Honest description: expiry *monitoring* with a shipped exit script, or a licensed access review with auto-remove — not an expiry the platform enforces.
* **A11 — service-account fencing has two modes, one per tenant.** Shared (default) is the existing CA500/CA501 on the shared group and location. Per-System adds CA500/CA501 SYSTEMNAME templates, one instance pair per system on its own `SG-CA-SA-<SYSTEM>` group and `VCIO-NL-SA-<SYSTEM>` location. In Per-System the shared CA500 and CA501 are set to **disabled**, not report-only — report-only still evaluates and would impose the shared location on a per-system account. The mode is declared in the manifest and both the gate (B3a) and the drift validator (C6) read it.
* **A12 — new `Deploy/manifest.example.json`.** Tenant ID, framework version, fencing mode, tenant object IDs for every group / named location / policy as created at import, the transition exit date and IDs, per-account CA501 owner and deadline, the expected Azure management-group and subscription inventory, and the partner tenant IDs. Real manifests live in `Deploy/<customer>/`, which is gitignored. Every tool in `Tools/` takes `-Manifest`.

### Gates

* **B1 — `-PreImport` is replaced by `-Gate <PreImport|SwitchReadiness|PostSwitch|Ring1|Ring2|Ring3|Ring4>`.** Each gate carries a fixed list of checks that are FAIL at that gate; the script exits non-zero on any of them. Checks outside the list still run and print, as INFO. **WARN never appears in a gate's list** — if something matters at a gate it is a FAIL there, and if it does not, it does not get to half-block the run. This removes the judgement call that "re-run and see if it looks OK" used to require.
* **B2 — the Ring 1 gate** now fails on: security defaults enabled; service-account coverage (B3a); fewer than two break-glass accounts, or any that is synced or disabled; a break-glass account whose Global Administrator assignment is **PIM-eligible rather than permanent** — checked through role management, because `Get-MgDirectoryRoleMember` cannot tell a standing assignment from an active activation, and an eligible-only break-glass account has to activate through the very sign-in path that is broken when you need it; any break-glass account without a FIDO2 credential; any enabled member user with no usable MFA method who is not a recorded worksheet exception; and any Directory Synchronization Accounts holder sitting in `SG-CA-ServiceAccounts`.
* **B3a — service-account coverage**, checked at SwitchReadiness, Ring 1 and every later gate. Structure per declared mode, then **evidence**: over the last 30 days of sign-ins the governing CA500 must appear in the account's applied-policies list (proving the fence reaches it, not merely that it exists), and nothing may succeed from outside the governing location. A blocked attempt from outside is desirable and is reported, not failed. An account with **no sign-ins in the window is UNVERIFIED**, reported by name, and the gate does not pass on UNVERIFIED — no data is not the same as no problem. An account in the CA002 exemption group with no enforced fence fails by name. A named location still holding an RFC 5737 documentation range is not a fence.
* **B3 — the Ring 3 gate** adds: every `ADMIN_ROLES` holder **and every `SG-CA-Privileged` member** has a phishing-resistant method registered, and E1's last run was clean — no uncovered privileged principal and no INCOMPLETE scope.
* **B4 — the Ring 4 gate** reads the App Protection **assignment collection**, not `isAssigned`, which only says something is assigned somewhere; it verifies an All Users assignment with no exclusion assignment that removes an `SG-CA-Users` member; it resolves the iOS/Android filter and compares its **rule text** against `app.deviceManagementType -eq "Unmanaged"` in include mode, because a filter renamed to look right is the failure worth catching; and it checks the targeted app list against the shipped JSON. SharePoint must return `AllowLimitedAccess`; every OWA mailbox policy any `SG-CA-Users` member is mapped to must be `ReadOnly` or `ReadOnlyPlusAttachmentsBlocked`, and a user on an unrestricted policy fails by name. A missing SPO or EXO module is a FAIL, not a skip — the gate cannot be assumed.
* **B5 — switching off Security Defaults is two gates**, because the readiness gate must pass while SD is still on. `SwitchReadiness` does not gate on SD and does gate on break-glass, registration readiness, B3a, CA000/CA001/CA002 being present and report-only, and every pre-existing enforced policy being mapped in the manifest. `PostSwitch` gates on SD off, those three enabled, a pilot sign-in showing CA002 applied with success in the last hour, and legacy-auth/device-code attempts showing CA000/CA001 failures — or none having occurred.

### Validators

* **C1** — the PowerShell validator globs `Transition/`, which the Python one already did.
* **C2** — transition lifecycle, drift validator, with the manifest. Fails when the group is non-empty after `exitDate`; when any transition policy is anything other than `enabled` while the group is non-empty, because the standard policies' exclusions are already live and only an enforced transition policy replaces them; and when one is left enabled over a long-empty group. Warns 30 days out. Membership it cannot read is UNVERIFIED and does not pass.
* **C3** — a policy with `includeUsers: ['None']` must have non-empty `agents.includeAgentUsers`, `clientApplications.includeAgentIdServicePrincipals`, or `clientApplications.includeServicePrincipals`. A non-null block with empty collections is still inert, and `agentIdRiskLevels` alone is not scope.
* **C4** — a `[compliantDevice, mfa]` OR-grant over a population inside CA002's scope is flagged REDUNDANT.
* **C5** — any device filter in a standard (non-`Transition/`) policy must equal `FILTER_COMPLIANT` exactly.
* **C6** — fencing mode, drift validator. Shared: shared CA500 enabled, no per-system instances except the permitted DirSync one, whose members must not be in `SG-CA-ServiceAccounts`. Per-System: shared CA500 and CA501 disabled, every `SG-CA-SA-*` group with an enabled CA500 instance.
* **Both validators now implement the same structural rule set**, plus required-identity presence per folder, the A10 transition pairing in both directions, the A9 instance-owns-its-exclusion-group rule, and MigrationTable completeness. **Neither gates on a policy count** — the tree count is printed for information only. A new CI workflow runs both against the repo on every change so they cannot disagree, and regenerates the tree to prove no JSON was hand-edited.

### Tools

* **E1 — `Tools/Compare-VcioPrivilegedScope.ps1`.** Enumerates Entra directory role assignments (active and PIM-eligible, built-in and custom, tenant- and AU-scoped, expanding group assignments) and Azure RBAC assignments (active and PIM-eligible, at management-group, subscription, resource-group and resource scope, via Resource Graph `authorizationresources` plus the eligibility API) for Owner, Contributor, User Access Administrator, RBAC Administrator, and every custom role carrying `Microsoft.Authorization/roleAssignments/write` or `*`. Diffs the union against `SG-CA-Privileged` plus the built-in role holders. Reports privileged-but-uncovered by name (FAIL), stale membership (WARN), and any expected scope it could not read or any live scope absent from the manifest (INCOMPLETE — the run is not clean, and B3 will not pass on it). Monthly, as the backstop to adding users at grant time.
* **E2 — `Tools/Invoke-VcioTransitionExit.ps1`.** Implements the transition exit in the only safe order: verify every member is in `SG-CA-Users` and that CA200/CA204/CA300/CA301 are enabled — any miss stops the run by name with the transition policies untouched — then export the roster and empty the group, then on later runs confirm a post-removal sign-in per removed user, and only then disable the transition policies. Elapsed time is never accepted as evidence; an unverified user leaves the policies enabled, which is safe over an empty group. Idempotent, `-WhatIf` supported. Schedule daily, or use a licensed access review with auto-remove.

## 2026.7.1 — 2026-07-09 (initial release)

**Lab-validated:** full import via IntuneManagement into a live tenant — 27 core + 6 overlay policies, 32 groups (created by dependency resolution), 3 named locations, agent-condition policies (CA600–602, CA704) and token protection (CA705) accepted by Graph; structural canaries verified in the portal (CA103 AND-grant with phishing-resistant strength + compliant device; CA203 every-time sign-in frequency); prereqs post-import gate green.

### Contents
* 27 core policies (Entra ID P1), 6 overlay policies (P2), 4 per-app extension templates (Restricted / Step-Up / Fenced / MAM-Mobile), 1 hybrid transition variant.
* 32 groups — break-glass, users persona, service accounts, one exclusion group per policy — with governance requirements embedded in group descriptions.
* 3 named locations, all deployment parameters (RFC 5737 placeholder IPs match nothing real).
* Companion App Protection baseline (iOS, Android, Windows/Edge) aligned to Microsoft Data Protection Framework Level 2, plus iOS/Android unmanaged-device managed-app assignment filters (no Windows filter — managed-app filters do not exist for Windows; Windows MAM assigns unfiltered by MDM-coexistence design).
* Prereqs script (`-Fix`, stage auto-detection, Graph SDK self-install): security defaults, break-glass verification, Intune Enrollment SP, TAP enablement, assignment filters, and App Protection creation via Graph — including the Windows MAM type, which IntuneManagement cannot import.
* Release validators (Python + PowerShell): inert scopes, GUID wiring, exclusion-group reuse, break-glass exclusions, encoding, placeholder escapes.
* Docs: implementation guide (A–E walkthrough with expected outputs), deployment parameters worksheet, operating runbook (four-ring enablement), onboarding (TAP / Autopilot hierarchy).

### Field notes from lab validation
* IntuneManagement imports iOS/Android App Protection but not `windowsManagedAppProtection` — prereqs script creates it via Graph.
* Managed-app assignment filters exist for iOS/Android only; `windowsMobileApplicationManagement` filter creation is rejected by Graph.
* Groups are dependency objects in IntuneManagement — no "Groups" import row; created during CA import via Replace Dependency IDs.
* Embedded sign-in windows and passwordless-only admin accounts don't mix — registration interrupts must be cleared in a real browser first (documented in the implementation guide).
